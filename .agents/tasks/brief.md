# Moonie 🌙 — Cute Watch Party & Virtual Hangout Website (HEAVY greenfield task)

Original user request (abridged where the original message was truncated): Build Moonie, a beautiful, fully functional, aesthetic Watch Party website. Friends hang out together, watch videos, share screens, play games, chat in real time. IMPORTANT: No authentication/login. No database. No user accounts. Users create and join rooms via shareable room links or room codes. Temporary room state + real-time communication. Keep architecture modular so auth and DB can be added later. Must be Vercel-deployable. Don't create just a static UI; implement functional features wherever possible.

## 1. Design & Theme
Cute, cozy, dreamy. Palette: pastel pink, lavender, baby blue, cream, soft white, light purple. Rounded corners, cute icons/illustrations, floating hearts/stars/sparkles, smooth animations, soft gradients, beautiful typography, cozy cards/buttons, subtle hover effects, responsive. Fonts Nunito/Quicksand/Poppins via next/font. Light mode + cozy midnight dark mode with working toggle persisted in localStorage (no flash on load). Respect prefers-reduced-motion. Feels like a Pinterest-inspired virtual sleepover, NOT a corporate dashboard.

## 2. Homepage
Moonie logo, navbar, hero, cute animated decorations, Create Room and Join Room buttons (working: open modals/flows), feature cards, How it works, footer. Hero heading: "Your little corner of the internet to watch, play & chill together." Subtitle: "Grab your favorite people, pick something to watch, and make memories together."

## 3. Room creation/joining
Create instantly without account; custom room name; pick cute room theme (theme actually changes the room's look); unique short human-friendly room ID/code (collision-checked on server); shareable invite URL (/room/[code]) with copy button; join by code OR pasted invite URL (parse both); optional password (enforced server-side); display name + avatar chosen on join (persisted in localStorage); see everyone inside; lobby screen before the main room (room name, theme, participants, host, name/avatar picker, password prompt if needed, 'Enter room' button). Handle room-not-found, wrong password, room full, connection failure gracefully. Room has a host who controls main playback. Room state is ephemeral, via real-time connection, no DB.

## 4. Watch together (MOST IMPORTANT) — media source selector with three tabs
A. YouTube: paste watch/youtu.be/shorts/embed URLs; robust ID parser as pure unit-testable function; official IFrame Player API loaded once; play inside room; sync play/pause/seek/position; host can change video; shared queue (anyone can add; host can reorder/remove/play next; auto-advance on end); loading states; handle onError codes 2,5,100,101,150 with friendly message and skip. Late joiner gets current video+position+state. Drift correction threshold ~1.5s with latency compensation using server timestamps. Respect YouTube restrictions.
B. Screen sharing: getDisplayMedia (entire screen / window / tab, audio when available); WebRTC P2P mesh: sharer creates an RTCPeerConnection per viewer, signaling relays offer/answer/ICE via targeted transport messages; late viewers get offered automatically; sharer can stop; handle browser native 'Stop sharing' (track 'ended'); show who is sharing and a clear LIVE indicator; handle NotAllowedError, unsupported browsers (mobile lacking getDisplayMedia), connection failures with retry, ICE restart, cleanup on leave. One sharer at a time; only the host can start sharing, with a clean documented path for host handover. MUST work across different devices/browsers: proper ICE server config, perfect-negotiation edge cases (queue candidates until remote description set).
C. Local video files: file picker + drag-and-drop (mp4, webm, mov where supported; validate via canPlayType, friendly message if unsupported); preview; custom controls (play/pause, seek bar, volume, mute, fullscreen); filename + size + duration; host-controlled playback sync. NO upload to any server; NEVER share blob URLs. Two flows, clearly explained in the UI: (1) 'Everyone picks the same file': host's file metadata (name, size, lastModified, optional quick hash of first/last chunks) is broadcast; each participant selects the same file locally; UI verifies match by name+size(+hash) then syncs playback; participants without the file see a clear prompt/dropzone. (2) 'Stream from host' P2P: host captures the playing video element via video.captureStream() and sends to participants over WebRTC, reusing the screen-share machinery; show caveats (Chromium/Firefox support; Safari limited) and fall back to mode 1 with an explanation. DataChannel chunked file transfer is optional, only if time allows.

## 5. Real-time sync
Sync playback state, play/pause, seek, current media source, screen-share state, participants, room events. Host-controlled (only host sends playback commands; others follow with drift correction). Late joiners receive full snapshot. Do NOT rely on React state alone: use a room-state store + transport events with message types defined in a shared types file. Vercel serverless can't hold WebSockets, so use a separate replaceable signaling service.

## 6. Live chat
Real-time sidebar: messages, display name + avatar, timestamps, built-in lightweight emoji picker (no heavy dep), cute bubbles, online count, join/leave system messages, typing indicators, auto-scroll with 'jump to latest' when scrolled up, responsive. In-memory only (server keeps a small capped recent-history ring buffer for late joiners, discarded with the room). Sanitize/limit message length; render as plain text.

## 7. Multiplayer games (Games section in every room, in-room picker, room-scoped ephemeral state, server-validated moves)
Ludo: 2-4 players, joinable seats, real board (CSS grid/SVG), animated dice, turns, correct rules (6 to leave home, safe squares, captures, home column, exact roll to finish, extra turn on 6), winner announcement, restart. Tic-Tac-Toe: 2 players, spectators allowed, turn indicator, win/draw detection, restart. Rock Paper Scissors: 2-player or multiplayer rounds, simultaneous hidden selection then reveal, winner, scores, next round. Game logic = pure typed testable reducers in a shared module used by the server (authoritative) and client (rendering). Small unit tests for pure logic (YouTube URL parser, Ludo rules, TTT win detection, RPS resolution) with a lightweight runner (vitest or node:test). Match the pastel design.

## 8. Room layout
Main player area; right-side chat; participant list; media source selector; queue; games; invite button; room settings (host can rename room, change theme, set/clear password, kick participant, transfer host). Desktop: main player + right sidebar with tabs (Chat / People / Queue / Games). Mobile: bottom tab bar or collapsible panels. Host migration if host leaves (oldest participant becomes host).

## 9. Stack
Next.js App Router, TypeScript, Tailwind CSS, Framer Motion (package 'motion' or 'framer-motion'), lucide-react, official YouTube IFrame Player API, native WebRTC, ephemeral signaling. Minimal other deps. No DB, auth provider, or permanent storage. All external config in env vars.

## 10. Vercel deployment
Next app at repo root deployable with zero config (no custom server, no hardcoded localhost). .env.example, README (local dev, env vars, deploying Next app to Vercel, deploying /signaling-server to Render/Railway/Fly step by step, setting NEXT_PUBLIC_SIGNALING_URL to wss:// URL and ALLOWED_ORIGINS on the signaling server, TURN setup, limitations: ephemeral rooms, mesh scale ~4-6 peers, local file caveats, how to swap transport and add auth/DB later). Security headers allowing YouTube iframe (frame-src youtube.com / youtube-nocookie.com) and Permissions-Policy allowing display-capture for self. Test the production build. Handle errors gracefully.

## 11. Code quality
Reusable components, modular, TypeScript types, separate media players, room management, chat, games, signaling. SSR-safe ('use client' for interactive parts; no window access at module scope); error boundaries, loading states, reconnect banner.

## ARCHITECTURE DECISIONS (already made, follow them)
- `SignalingTransport` TS interface (connect, join room, send/broadcast/targeted message, presence, events, disconnect, reconnect) under src/lib/signaling/. Default impl: standalone Node WebSocket server (package 'ws') in top-level /signaling-server with its own package.json, simple deploy to Render/Railway/Fly (no Dockerfile required), /health endpoint, CORS/origin allow-list via env (ALLOWED_ORIGINS), in-memory room state only, room cleanup when empty, room password check server-side with hashed value held in memory only, message size and rate limits. Client reads NEXT_PUBLIC_SIGNALING_URL (ws:// or wss://); no hardcoded localhost in code (only documented default in .env.example / dev script). Provide `npm run dev:all` running Next + signaling locally. Optional NEXT_PUBLIC_STUN_URLS / NEXT_PUBLIC_TURN_URL / NEXT_PUBLIC_TURN_USERNAME / NEXT_PUBLIC_TURN_CREDENTIAL for ICE (default public Google STUN); document TURN is needed for strict NATs. Document swapping transport for Ably/PartyKit/Liveblocks. Thin 'identity' module (local display name+avatar in localStorage) so auth/DB can be added later.
- Room state authoritative in signaling server memory (host, participants, current media, playback state, queue, game states, chat ring buffer).
- Shared types/logic in a /shared folder (or equivalent) importable by both Next (works on Vercel) and the signaling server's build.
- Folder layout: src/components (landing, room, media players, chat, games, ui), src/lib (signaling, webrtc, youtube, room, identity, games), src/app routes.
